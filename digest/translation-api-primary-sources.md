# Translation API facts for the report-pipeline review

Checked 2026-09-06. This note records provider behavior, not a measured comparison of translation quality on our reports. Repository-specific findings belong in the accompanying branch review.

## Google Cloud Translation

- **Input format must be explicit.** Basic v2 defaults to HTML unless `format: "text"` is supplied; Advanced v3 defaults to HTML unless `mimeType: "text/plain"` is supplied. Both automatically detect the source language when it is omitted. Basic defaults to NMT. These defaults are API behavior, not evidence that a particular report was mistranslated. [Basic REST reference](https://docs.cloud.google.com/translate/docs/reference/rest/v2/translate), [Advanced REST reference](https://docs.cloud.google.com/translate/docs/reference/rest/v3/projects/translateText).
- **HTML handling is substantive.** The service translates text between HTML tags and preserves tags; other markup such as XML has undefined results. For raw reports, explicitly use plain text and inspect preserved comparison signs and any entity escapes in the actual outputs. The inspection recommendation is an engineering inference. [Translate text](https://docs.cloud.google.com/translate/docs/basic/translating-text).
- **Request limits are separate from encoder token limits.** Google recommends at most 5,000 code points per synchronous request; Advanced has a 30,000-code-point maximum, Basic a 100,000-byte request maximum. Oversized requests fail with `400 INVALID_ARGUMENT`; quota exhaustion is also an error. Basic supports at most 128 strings per request. Therefore, an application that stores source text after exceptions can silently mix untranslated reports into a nominally English corpus; this is a client failure mode to check, not documented API fallback behavior. [Quotas and limits](https://docs.cloud.google.com/translate/quotas), [Basic REST reference](https://docs.cloud.google.com/translate/docs/reference/rest/v2/translate).
- **Domain terminology can be controlled in Advanced.** Glossaries specify consistent domain-specific translations; matches are case sensitive by default, some stopwords are ignored, and glossary resources do not provide version control. A glossary is an option for ambiguous anatomical terms, but cannot establish preservation of all negations, uncertainty, or relationships without evaluation. Retain the exact glossary file and version if used. [Glossary guide](https://docs.cloud.google.com/translate/docs/advanced/glossary).
- **Do not equate the Cloud API with the consumer website.** Google's Cloud Translation FAQ says submitted content is used to provide the service, held briefly in memory, and is not used to train or improve Translation features. This does not establish that the particular project's report export has institutional authorization; it does remove a basis for claiming that Cloud Translation inherently trains on submitted reports. [Data usage FAQ](https://docs.cloud.google.com/translate/data-usage).

## Claude Code CLI: preserving the actual branch pipeline

The reviewed branch uses `claude -p`, not the Anthropic Messages API. A bounded pool of the same CLI subprocess calls is the closest parallel execution design. Moving to the Message Batches API would change the execution environment and authentication and is a separate migration, not the exact same pipeline.

- **Pin the resolved model, not just the alias.** `opus` is a configurable alias that updates over time and may resolve differently by provider or `ANTHROPIC_DEFAULT_OPUS_MODEL`. Record the actual model and Claude Code version for each run; agree on a full model ID across machines. [Model configuration](https://code.claude.com/docs/en/model-config).
- **JSON is an envelope.** `--output-format json` returns the text in `result` with session metadata. A schema-constrained response is a separate `--json-schema` feature using `structured_output`. Failures can be printed as the result on stdout, so inspect exit status and failure metadata before accepting text. Cost fields are client estimates. [Programmatic usage](https://code.claude.com/docs/en/headless).
- **The current flags isolate tools, not all host context.** `--tools ''` disables built-in tools, and `--strict-mcp-config` restricts MCP configuration; `--system-prompt` replaces the system prompt. [CLI reference](https://code.claude.com/docs/en/cli-reference). However, `CLAUDE.md` is delivered separately as user context, so replacing the system prompt does not by itself establish identical input context across hosts. [Memory documentation](https://code.claude.com/docs/en/memory).
- **Inspect the installed CLI before adopting newer isolation flags.** Current docs describe `--bare` as skipping automatic discovery of hooks, skills, plugins, MCP servers, memory, and CLAUDE.md. But it also skips OAuth credentials and the system keychain, requiring API-key/provider authentication. Adding it blindly can break a subscription-backed teammate workflow. Preserve existing execution semantics first; standardize the working directory and audit inherited instructions/settings. [Programmatic usage](https://code.claude.com/docs/en/headless).
- **Concurrency consumes shared allowance.** Official docs support parallel sessions and state that running several multiplies token usage. Subscription allowances and API/provider rate limits are distinct; quota exhaustion blocks requests, while 429 throttling requires reducing concurrency or waiting. There is no universal safe CLI worker count established by these pages. Start with a small bounded pool, checkpoint individual successes, and back off on throttling; these are implementation recommendations. [Parallel agents](https://code.claude.com/docs/en/agents), [Error reference](https://code.claude.com/docs/en/errors).

For the same pipeline, preserve source cleanup, prompt bytes, model, CLI flags, and output parsing. Give each subprocess one report, capture output independently, and have one coordinator write successful translations keyed by immutable source identity. Do not have several processes rewrite the same JSON checkpoint. Record source hash, prompt hash, actual model, CLI version, and execution identity so results from two machines can be reconciled. These are engineering implications, not a provider guarantee of byte-identical generated translations.

## What these sources cannot establish

Provider documentation cannot establish that Google is worse than Claude for this corpus, or that either preserves every imaging finding. A useful paired audit translates the same original reports with each pipeline and reviews negation, anatomical structure and compartment, laterality, severity, uncertainty, measurements, missing sections, and added findings. Also measure English-encoder token lengths and collisions between distinct source reports. These are proposed corpus checks inferred from contrastive pair supervision: a fluent translation that changes the depicted finding gives the image an incorrect positive text target.

Keep source-to-study identity and train/validation/test membership fixed. Compare a complete Google corpus with a complete Claude corpus instead of silently mixing providers according to API failures. If work is split across machines, shard deterministic source IDs, retain source hashes and translation provenance, and reconcile duplicates before building the downstream report file. No paid translation calls were made for this research.
